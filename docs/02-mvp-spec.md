# Wear There — MVP Spec

**Status:** Draft v1 · **Release goal:** shareable link that 5–10 friends can use unaided

This document defines exactly what ships in v1. If a feature isn't listed under "In scope," it does not ship — additions require consciously bumping something else out.

## 1. In-scope features

### F1. Preference survey (~11 questions)

One-time, stepped survey completed on first visit. Editable later from a "My style" screen. Stored in the browser (localStorage) — no account. **Answers persist across visits** — the survey is answered once, not every time (see F5 note on how storage works).

Draft question set (final wording in UX spec):

1. Where's home? *(city type-ahead — anchors all weather comparisons: "22°C in Lisbon" means something different to someone from Glasgow vs. someone from Athens. Enables phrases like "warmer than home right now")*
2. Do you generally run hot, cold, or average? *(3-way)*
3. At what temperature do you switch to summer clothes (shorts/dresses)? *(slider, °C)*
4. At what temperature do you need a proper coat? *(slider, °C)*
5. How much does humidity/mugginess bother you? *(scale 1–5)*
6. Rain plan: hood, umbrella, or "I just get wet"? *(choice)*
7. Your style, most days: casual / smart-casual / dressy / sporty *(choice, pick up to 2)*
8. Warm-weather staples you actually wear *(multi-select: linen shirt, sundress, shorts, sandals, …)*
9. Cold-weather staples you actually wear *(multi-select: wool jumper, puffer, boots, scarf, …)*
10. Layers or one big coat? *(choice)*
11. Packing philosophy: pack light and re-wear vs. options for every scenario *(scale)*

**Acceptance:** survey completable in under 3 minutes on a phone; answers persist across visits; skippable questions have sensible defaults.

### F2. New trip

- Input: destination city (type-ahead search) + start and end dates + **trip purpose**.
- Trip purpose *(pick up to 2)*: City break · Beach · Outdoors/hiking · Wedding or formal event · Business · Visiting family. Purpose directly shapes the packing list — a wedding adds formalwear (outfit, dress shoes, accessories); a hiking trip adds outdoor gear (boots, technical layers, daypack).
- Geocoding and forecast from Open-Meteo (free, keyless).
- v1 supports trips **starting within the 14-day forecast window**. Dates beyond that show a friendly "Too far out for a real forecast. Check back nearer the time." message (climate-averages fallback is a v1.1 candidate).
- Trip length capped at 14 days.

**Acceptance:** ambiguous city names (e.g. "Paris") show a short disambiguation list with country; invalid dates are prevented, not error-messaged.

### F3. Personalised forecast ("feels like, for you")

- Daily strip for the trip dates: high/low, apparent temperature, humidity, rain chance.
- Each day translated into a personal comfort chip using the survey profile — e.g. "Hot for you", "Cold for you — layer up", "Muggy + brolly" — with the chip's colour driven by the same feels-like number (see UX spec gradient system).
- Personalisation v1 = comfort offset: shift apparent temperature bands by the user's stated thresholds and hot/cold tendency. No ML.

**Acceptance:** two profiles with different thresholds produce different phrases for the same forecast.

### F4. AI packing list

- Generated by one Claude API call combining: personalised forecast summary, trip length, **trip purpose**, and the preference profile.
- Model: Claude Haiku 4.5 (cheapest current model, ~half a penny per list) with structured JSON output enforced by the API, so the response is always a valid list — see the Technical Design for details.
- Output: categorised checklist (Tops, Bottoms, Outerwear, Footwear, Accessories, Essentials) with quantities ("3× t-shirts") and a one-line *why* for non-obvious items ("Umbrella — 60% rain chance Tue–Wed").
- Items are tick-boxes; ticked state persists on the device.
- Regenerate button (with confirmation, since it resets ticks).

**Acceptance:** list respects stated style, staples, **and trip purpose** — a wedding trip includes a formal outfit section, a hiking trip includes outdoor gear, and a "dressy" profile isn't told to pack cargo shorts; generation completes in under ~15 seconds with a styled loading state; API failure shows a retry, never a blank screen.

### F5. My trips

- Up to 10 trips saved on-device: destination, dates, purpose, generated list, tick state. Adding an 11th prompts the user to delete an old one.
- Reopen a trip to continue ticking; delete a trip from the saved set (with undo).
- **How storage works (no login needed):** preferences and trips live in the browser's localStorage, which persists indefinitely across visits — the user answers the survey once and it's remembered every time they return. Data is only lost if they explicitly clear the site's data, use private browsing, or switch to a different device/browser. No FAQ needed; the app just works. Cross-device sync is the one thing this can't do — that's the v2 trigger for accounts, if friends ever ask for it.

### F6. "Bright Line" design & polish

- Mobile-first, works down to 360px wide; presentable on desktop.
- Bright Line visual language per the UX spec: Bricolage Grotesque + Plus Jakarta Sans, white surfaces, and the temperature gradient system (cold pale→deep blue, hot yellow→red, no purple/green) driven from the feels-like number.
- The forecast and packing list screens must look good in a screenshot — those are the shareable artifacts.

## 2. Explicitly out of scope (v1)

| Cut | Why | Revisit |
|---|---|---|
| Accounts, login, cross-device sync | Cost, complexity, privacy burden | v2 if friends ask for it |
| Shopping/purchase suggestions | Needs wardrobe knowledge to avoid suggesting owned items | v1.1 — flag "you may not own this" items |
| Multi-stop trips | Doubles trip-model complexity | v2 |
| Climate averages for far-future trips | Extra data source | v1.1 |
| Native iOS/Android apps | Web reaches everyone free | Only with real traction |
| Sharing lists between users | Screenshot covers it | v2 |
| °F support | Audience is UK friends | v1.1 toggle, trivial |

- [ ] Claude API key server-side only, spending cap set
- [ ] Tested on iPhone Safari + Android Chrome
